# 配置とルーティングの方針

## 現在の方針：通常配置を優先し、難所だけ段階探索する

通常配置 → 難所判定 → 同じ観点の組み合わせ → 未解消なら異なる観点の組み合わせ、の順にする。以降の過去節にある全順列108候補は履歴であり、現在は使用しない。

各塊の内部順序は最大3パターン。接続ラベルの観点ごとにソース内の登場順を使い、同じ順序をまとめる。対応する観点名はすべて保持し、両側に共通する観点の組み合わせを先に評価する。無ラベルでは接続の登場順を一つの観点にする。語の同義判定・自然言語による意味推論は行わない。

まず実際の通常経路を評価し、共有区間の合計32超、進行方向に逆らう移動の合計24超、または直交する交差が2箇所以上の場合に探索する。単位はSVG座標。これらは今回の適用を開始するための暫定しきい値であり、ユーザー試験で確定した基準ではない。ラベルの混雑のみの難所は現状この判定では検知できない。

同観点の候補を評価した結果、上記の難所条件が解消していれば異観点へ進まない。残る場合のみ、まだ評価していない異観点の組み合わせを試す。改善しない候補は採用しない。3×3パターンと最大3形状で、1組あたり最大27候補（05では2×3×3=18）に制限。通常配置の初回評価は別途1回必要。最大4組という全体上限、保存位置・固定・明示指定の尊重は維持する。

現在の呼び出し対象は縦方向graphの配置経路。難問モードをすべての図種へ追加したわけではない。コンテナ方向やポートを明示した06へ勝手に適用しない。

[比較実験](../reports/search-benchmark/report.md)の時間は当時の実験方式の実測値であり、この段階判定を含む製品実装の速度保証ではない。


配置は「意味のある塊を作る → 塊同士の接続を組み立てる → 余白で読みやすく調整する」の順で考える。

## 優先順位

1. 明示された配置・順序・接続ポート・ルーティング方針と保存位置を尊重する。
2. 包含・継承・並列・正常経路・再試行など、構造上のまとまりを捉える。根拠のない主経路やグループを作らない。
3. まとまり同士の接続と、独立した分岐の入口・出口を組み立てる。
4. 通路・ラベル・境界に必要な余白を配分する。局所拡張で別の衝突を作らない。
5. 読みやすさが同程度なら、不要な迂回や余白を減らす。

交差数や面積だけでは良否を決めない。独立した接続の長い共有は識別を妨げる一方、forkの意味に沿う共有や明確な交差は許容できる。余白を増やしても改善しない場合は、まとまりの捉え方と接続方法へ戻る。

## 今回の実装

縦方向のフローチャートに対し、既存の主経路判定後に単純な再試行のまとまりを認識する。

- 主経路の判断から枝ノードへ入り、そのノードから主経路の先行ノードへ戻る、一入口・一出口の枝を対象にする。
- 枝ノードを戻り先と判断の中間の高さへ配置する。左右は既存の側を保ち、ノード外形から必要な離隔を確保する。
- 正常経路の位置と接続情報は変更しない。経路とラベルはその後の既存処理で生成する。
- 空間不足・周囲との衝突がある候補は採用しない。
- 保存配置、固定、包含、明示順序や配置ヒント、明示接続ポート・layoutDirectionのある場合は新処理を適用しない。

処理はsrc/directed-layout.tsのarrangeRetryBlocks、呼び出しはsrc/layouts.tsの縦方向配置にある。既存の意味的配置、端点選択、ラベル配置、deployment通路拡張を置き換えるものではない。

## 適用範囲

多段の再試行、複数入口・出口、一般の多対多グラフを今回の規則で自動最適化しない。05の多対多配置や06のコンテナ方向を変更する一般的な探索は未実装。手動修正版の座標を特例として埋め込まず、ソースの接続関係に基づく適用範囲を増やしていく。

設計の根拠：[余白の分析](../reports/layout-review-01/whitespace-method.md)、[過去修正との照合](../reports/layout-review-01/whitespace-retrospective.md)。初回の採点と描画バンドルは比較基準として保持する。

## 05・06への適用（2026-09-12）

05ではgraphの接続から「入力を持たない群」と「出力を持たない群」を認識し、密な二部接続の場合に群間の通路と群内間隔を確保するarrangeBipartiteBlocksを追加した。読み方向を保持し、ラベル名には依存しない。平坦・24ノード以下・各群2個以上・接続密度75%以上に限定する。包含、配置ヒント、明示ポート、保存配置がある場合は適用しない。現在の間隔は接続本数に基づく上限付きヒューリスティックであり、ラベル実寸や区間別並走数を使う最適化ではない。

比較用05は読み方向をLRから下向きに変更した。これはソースでの方向選択であり、エンジンが明示LRを無視して上下へ変更するものではない。

06では比較用ソースの入口をrowからcolumnへ変更し、購読をfromPort=right/toPort=bottomで接続する。既存機能で意味と接続意図を表現した試験で、コンテナ方向やポートの自動推論を新規実装したわけではない。購読の下側の大回りは小さくなったが、Workerの下に入る購読とDBへ出る更新が近接する課題が残る。

初回と手動修正版は維持し、reports/layout-review-01/05-dense-current.htmlと06-deployment-current.htmlで確認できる。両図とも初回より見通しは改善したが、手動修正版を超えたとは評価しない。

## 隣接する塊の内部順序を共同で選ぶ（2026-09-12）

方針を「意味のある塊を決める → 接続する塊双方の内部順序をセットで比較する → 経路と余白を整える」とする。片側の並びを固定してもう片側だけを整える方式だけに頼らない。

src/paired-block-order.tsのorderConnectedBlocksをgraph/deploymentの自動配置へ追加した。各塊2〜3要素について両側の順列の直積（最大36候補）を比較する。対象は直接接続する同階層のコンテナの子要素、または平坦な二部グラフの入力群・出力群。コンテナの位置・所属・大きさは維持し、要素を既存の中心位置へ割り当て直す。異なる大きさの要素が枠外へ出る、または兄弟と衝突する候補は不採用。

候補ごとに全接続を既存ルーターで再計算し、異なる線の共有長を優先して抑え、その後に交差・折れ・距離を既定の重みで比較する。他の塊への接続も評価対象とし、同点では並びを変えない。ラベル重なりはこの候補評価にまだ含まれないため、最終描画の確認を必要とする。端点付近の共有も計測に含む保守的な近似であり、人の読みやすさの完全な測定ではない。

明示順序・行列指定、grid、明示ポートや経路方針、保存配置・固定がある場合はその制約を優先する。全体30ノード・40接続、4組までに探索を制限する。候補間で改善した組を順次確定するため、多数の塊を含む全図の大域最適性は保証しない。

05では全対全のため抽象的な交差数は同率になりやすい。実際の経路の共有・迂回を含めて候補を比較する。06の比較候補では前回追加した明示ポートを外し、内部順序の共同選択を試す。明示ポートを保持した既存のcurrentページは、この新処理の対象外として維持する。

### 今回の描画確認

05-dense-paired.htmlではAPI群とDB群の両側の順序が変わった。独立線の共有・迂回の評価で採用された候補だが、上部に横断線が残り、ラベルを含む目視評価で全面的に改善したとは断定しない。

06-deployment-paired.htmlは購読の明示ポートを外した条件で比較したが、内部順序は維持された。購読の外周迂回が残る。順序の共同選択だけでは解消できず、ポートと通路の候補も比較することが次の課題。前回の明示ポート付き候補を超えたとは扱わない。

型チェック・全728テスト・ビルド成功。両比較ページのブラウザーエラー0件、PNGを目視確認した。

## 順序候補に段差・接続側を含める（2026-09-12）

順序を先に確定して後から補正する方式を改め、各順序と段差・接続側の組み合わせを一つの候補としてルーティングする。

今回の段差探索は平坦なgraphの3要素対3要素に限定。双方の全36順序について、整列＋自動ポート、中央の受け側を48手前・端の送り側を32奥へずらす＋自動ポート、同じ段差＋進行方向の出口／入口の3候補（最大108）を評価する。その他の対象では順序と自動／進行方向ポートを比較する。段差の位置はスロット基準であり、特定のAPI名・DB名には依存しない。

長い共有区間の削減だけが上方迂回に勝つことを避けるため、評価を共有長×6＋進行方向に逆らう移動長×12＋交差数×120＋折れ数×48＋線長に変更した。これは目視比較に向けた暫定重みであり、読みやすさを保証する尺度ではない。

接続側は探索用LayoutModelのコピーで指定し、選んだコピーを最終ルーティングへ渡す。元のソース・モデルを改変しない。明示ポート等の既存指定は優先する。通路は各候補のルーターが生成した結果を評価する方式で、通路座標自体の連続最適化は未実装。ラベル混雑の直接採点も未実装。

今回の呼び出しは縦方向graphの配置経路にある。前節に記したdeployment一般への接続は現コードで確認できなかったため、06への段差・ポート共同探索まで実装済みとは扱わない。比較用ページは05-dense-search.html。初回PNGや手動SVGは変更していない。

候補増加に伴い探索を2回行う回帰テストの専用タイムアウトを20秒へ変更した。実装の探索上限自体は108候補。速度改善には候補の事前選別や経路評価の再利用が必要。
